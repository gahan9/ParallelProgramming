  ulp(1) is 9.766e-04 in fp16 and 7.812e-03 in bf16, so any update smaller than half
  of that rounds straight back to 1.0. A learning rate of 1e-3 against weights
  of order 1 is exactly this regime - which is why mixed-precision training
  applies the update to an fp32 MASTER copy and only casts down for the next
  forward pass. Note the ordering: fp16 keeps more of these than bf16, because
  precision near 1.0 is a mantissa question, not a range question.

  fp64 GPU result vs a long-double host sum in the same order: PASSED (<=1e-12 rel)
  The fp16 column is the lesson. Its error grows with n because every one of
  the n additions is rounded onto a grid with only 10 mantissa bits, and once
  the running sum is large enough, each new term is smaller than half an ulp
  of it and contributes NOTHING. This is why matrix cores multiply in 16 bits
  but accumulate in fp32: the product is cheap to narrow, the SUM is not.

[7] Catastrophic cancellation: one-pass variance (kernel 0.319 ms)

  data          : 4096 values, x = 1e+06 + Uniform(-1, 1), so var(x) = 1/3
  E[x^2]-E[x]^2 in fp32 : 40177532.000000000   <-- garbage (sometimes negative!)
  E[x^2]-E[x]^2 in fp64 :        0.335386986   <-- the same formula, wider accumulator
  two-pass in fp32      :      957.956542969   <-- FAILED

  Both fp32 sums are individually accurate to ~7 digits. The subtraction
  destroys them: E[x^2] and E[x]^2 are both about 1e12 and agree to 12
  digits, so their difference keeps almost no correct digits at all. The fix
  is algebraic, not numeric - subtract the mean FIRST, while the operands are
  still small. No amount of extra precision makes an unstable formula stable;
  fp64 only moves the cliff.

  Read the accuracy columns first. fp16 and bf16 storage both stay within the
  error their own mantissa allows, and bf16's error is about 8x fp16's - exactly
  the ratio of their ulp(1) (2^-7 vs 2^-10). Now read the last row: the same
  fp16 storage with an fp16 ACCUMULATOR is far worse, because 1024 roundings of a
  growing sum compound. Storage precision costs you a bounded relative error;
  accumulator precision costs you the whole result. That single asymmetry is why
  every matrix core multiplies narrow and accumulates in fp32.

  Now read the throughput columns, and be suspicious. Global traffic halves
  exactly as the byte accounting predicts, but the GFLOP/s should move far less
  than that (how much less depends on your GPU): at a 32x32 tile this kernel is
  limited by LDS traffic and VALU issue rather than HBM, and it never touches the
  matrix cores. Narrower operands only buy time where BYTES are the limit - which
  is what [B] shows - or where a matrix-core path exists to consume them, which is
  what hipBLASLt / cuBLASLt do and this kernel does not. README section 5.

  This is the roofline result from B02, in one table: the kernel moves 3 elements
  per FLOP, so it sits far to the left of the ridge point and its ceiling IS the
  bandwidth divided by the bytes per element. Halve the element width and the
  ceiling doubles, so the time should approach half - expect a speedup near 2x but
  short of it, because the GB/s column shows both variants are already close to
  the same HBM limit and the fp16/bf16 runs have less work to hide launch and
  scheduling overhead behind. Compare the GB/s across rows: if they match, you are
  bandwidth-bound in both and the speedup is purely the byte count.

  Neither table is a benchmark of your GPU. Run it on yours; the SHAPE (bytes
  halve, error grows with the reciprocal of mantissa bits, fp16 accumulate loses)
  is what transfers.
